# Dev log — phase 2

Phase 1's log is in [../phase1/DEVLOG.md](../phase1/DEVLOG.md). This one covers the rebuild that started in September 2026, and unlike phase 1's it is being written as the work happens rather than reconstructed afterwards.

---

## 2026-09-04 — deciding what phase 2 actually is

Started from the two dead ends phase 1 hit: GTD only records attacks that happened, so there is nothing to train "will something happen here" against, and there was no way to judge whether 68% accuracy was good. Both come from not knowing the answer.

The fix is to generate the data. If I write the rules, I know exactly what structure is in there.

### Rejected — asking an LLM to invent a dataset

The first version of this idea was to have a separate AI invent fictional organisations and their activity records, on the reasoning that an AI with no knowledge of the project could not bias the data toward a desired result.

That reasoning is right about contamination and wrong about validity. Data generated by an LLM contains the patterns the LLM put in, and a model trained on it discovers the generator's habits rather than anything structural. Using a *different* AI does not change that — the problem is not who generated it, it is that nobody knows what the rules were.

So: write the generative rules explicitly, in code. Then the ground truth exists as a file, and the question becomes "does the model recover the structure I planted", which is measurable.

### The signal ladder

Planting a single structure would produce a single uninformative number. Instead, four levels, each needing strictly more data to detect than the last:

| Level | Structure | Minimum columns |
|---|---|---|
| 1 | Fixed operating area per organisation | lat, lon |
| 2 | One organisation's centre migrates over time | + date |
| 3 | Seasonal suppression, target preference | + target_type, month |
| 4 | Command directives changing behaviour in bursts | all, per organisation |

The deliverable stops being an accuracy figure and becomes the *deltas* between feature sets. That is the actual answer to "which data do you need to collect".

### Three organisations

NORTHWIND is deliberately the easy case — static base, one branch, no time signal. It is the control: if a coordinates-only model cannot classify it, the pipeline is broken rather than the data being hard.

TIDEBREAK carries the level-2 signal and is the one the whole phase turns on. Its base drifts east 0.5 km/day along a real island chain, about 900 km over five years. Coordinates alone smear it across the whole chain; add the date and it resolves. That delta is the headline number.

DRYSTONE gets seasonality and a target preference, plus an air branch with 600 km reach so it separates from NORTHWIND on range alone.

### The ceiling — the piece I initially missed

The first draft of the spec required a majority-class baseline next to every accuracy, which was the lesson from phase 1. That is the floor: what you get for free.

I had left out the ceiling, and it turns out to be the more interesting half. The organisations' territories genuinely overlap, so some events are irreducibly ambiguous and no model can resolve them. Because the generative rules are known, an oracle classifier can be built that computes each organisation's probability of producing a given event, and its accuracy is the best physically achievable score.

That reframes every result. A model at 68% between a floor of 59.5% and a ceiling of 74.2% has captured 8.5 of the 14.7 points that were available, not 68 out of 100. Phase 1 could not make that statement about anything.

### Known-null column

`success` is fixed at 72% across all organisations and carries no signal by construction. Any method that finds structure in it is overfitting, and having a column with a known-empty answer is how that gets caught.

## 2026-09-04 — visual prototype

The spec described the interface in prose, which is not enough to hand to an implementer for something whose whole point is that it looks like an instrument. Built a working prototype instead: [../../phase2/prototype/index.html](../../phase2/prototype/index.html).

### One palette rule

Saturation belongs to organisations and nothing else. Every surface, control, label and timeline element is neutral slate; active and hovered states shift brightness rather than picking up a colour. The consequence is that any colour on screen means exactly one thing — which organisation — and the eye never has to ask whether an orange element is a warning or a cell.

Chose IBM Plex for all three roles (Condensed for uppercase labels, Sans for interface text, Mono for every number and coordinate). It was designed for technical contexts, which is a reason beyond taste.

Military document conventions are used as content rather than decoration: DTG timestamps (`121200Z JUL 28`), three-digit zero-padded ranges and counts, callsign abbreviations in the activity feed.

### Bugs found by actually looking at it

Writing it was not enough — three real defects only appeared in a screenshot of the running page.

**Terrain was invisible.** Land was drawn as a dot grid at `#1E2C37` on a `#070B0F` ground, which at that contrast reads as noise rather than continents. Fixed by layering: a filled polygon underneath so landmasses read as shapes, a brighter 1° dot grid on top for texture, and coastline-adjacent dots brighter still so outlines emerge on their own. Also added region and ocean labels following chart convention, where ocean names are dimmer and more widely tracked than land names, plus degree labels on the graticule.

**The timeline was cut off.** `.wrap` had `height:768px` hardcoded with `overflow:hidden`, so on any viewport shorter than that the bottom row was simply clipped away. Changed to `100vh` with a min and max.

**Zoom was locked at the wrong scale.** This one was the most instructive. The map opened at 0.6 px/deg with the whole world drawn tiny in the middle. The cause: the script measures the stage and computes a fit-to-world zoom at startup, but inside the artifact iframe the element still has near-zero height at that moment, so it fit the world to a 200 px box and never recomputed. Window `resize` did not reliably fire when the host later sized the iframe. Fixed with a `ResizeObserver` on the stage, and by treating fit-to-world as a hard minimum zoom that gets re-applied whenever the viewport changes rather than a one-time calculation.

That third one is worth remembering generally: **measuring layout during script execution is unreliable in an embedded context, and `resize` is not a substitute for observing the element you actually care about.**

### Performance

The dot grid is ~8,600 land points, each requiring a point-in-polygon test against 22 landmass polygons plus eight more tests to decide whether it is coastal. Computing that on every repaint made panning unusable. It is now computed once into a cached array in lat/lon space, which is projection-independent, so pan and zoom only re-project and redraw.

The accumulated-events layer is a separate offscreen canvas that is appended to rather than redrawn per frame, and it is reset and replayed only when the camera or the playhead moves backwards.
